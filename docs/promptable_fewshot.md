# Cross-image visual few-shot detection

For the full experiment status and command-by-command reproduction runbook, see [the reproducibility report](promptable_reproduction_report.md).

This experiment gives the model one or more **support image + box** examples and asks it to localize that concept in separate query images. The query-image ground-truth boxes are used only by the training loss and evaluation code; they are never passed to the support/query model forward call or inference CLI.

The implementation is isolated in `src/rfdetr_promptable`. The original `src/rfdetr` package is unchanged. `experiments/promptable_v1/` is the frozen same-image v1 snapshot; v1 metrics are not evidence of cross-image generalization because v1 prompts with the query image's own box.

## Model behavior

- Support image features are pooled inside each supplied support box with ROIAlign; box geometry is encoded alongside the visual ROI.
- Multiple support shots with the same group ID are averaged into one concept representation. Each query image selects its concept via `query_to_support` and receives an independent learned DETR query/reference bank.
- Support coordinates are not reused as query reference points. Query GT boxes are not inputs to model forward/inference.
- RF-DETR detection/query/box task weights are randomly initialized (`pretrain_weights=None`). The RF-DETR Base DINOv2 backbone loads its pretrained backbone weights at the configured 560-pixel resolution. No pretrained RF-DETR detection checkpoint is loaded.
- Training samples positive episodes and absent-class negative episodes. `negative_ratio` is the expected negative-to-positive ratio (0.5 means one negative for every two positive episodes on average).

## COCO class split

The split is generated by `scripts/generate_coco_prompt_split.py`:

- Train/seen classes: COCO IDs `1, 3, 8, 9, 10, 11, 13, 14, 15, 16`.
- Held-out test classes: COCO IDs `17, 18, 19, 20, 21, 22, 23, 24, 25, 27`.
- Class sets are disjoint. Training uses up to 10,000 train images; seen validation and held-out test use all available val images containing their respective classes.

Generate the filtered annotation files if needed:

```bash
uv run python scripts/generate_coco_prompt_split.py \
  --train-source-annotation datasets/mscoco/annotations_trainval2017/annotations/instances_train2017.json \
  --validation-source-annotation datasets/mscoco/annotations_trainval2017/annotations/instances_val2017.json \
  --output-dir datasets/mscoco_prompt_split \
  --train-classes 1 3 8 9 10 11 13 14 15 16 \
  --test-classes 17 18 19 20 21 22 23 24 25 27 \
  --train-images 10000 \
  --seed 7
```

## Train, validate, and test

The Python configs in `configs/` expose a `cfg` dictionary; pass one with `--config`. Explicit CLI options override values loaded from the config. The one-shot baseline command is:

```bash
uv run python scripts/train_promptable_fewshot.py \
  --config configs/promptable_fewshot_1shot.py --device cuda
```

For a 1–5-shot training distribution, use `configs/promptable_fewshot_5shot.py`; evaluation uses up to five distinct support images for every concept. For the negative-heavy setting, use `configs/promptable_fewshot_negative_heavy.py`.

The runner selects the checkpoint with the best seen-validation episodic macro positive IoU, reloads it, then writes final episodic validation/test metrics and standard COCO bbox metrics to `<output stem>.metrics.json`. `seen_validation_coco` and `held_out_coco` contain per-category COCO AP/AP50/AP75, AP by object scale, and AR at maxDets 1/10/100, plus macro-averaged mAP/mAP50/mAP75, scale-specific mAP, and mAR. The standard COCO evaluator ranks up to 100 detections per category/image and computes the official 101-point interpolated AP over IoU thresholds 0.50:0.05:0.95. Each category uses a deterministic support set; the union of all support image IDs is excluded from one common query set. Every other COCO validation image—including absent-class images—is evaluated for every category, so per-class AP values share the same query images. Use `--coco-eval-batch-size` to trade evaluation speed for GPU memory.

Held-out qualitative figures go under `<figure-dir>/heldout_test/{original,prediction,prediction_gt}/<class>/`. Set `--negative-eval-per-class 0` to disable sampled absent-class episodes for the supplemental episodic presence metrics; COCO AP still evaluates every query image.

## Metrics and interpretation

For each positive `(category, query image)` episode, the scorer ranks the model's query boxes by objectness and evaluates its top-scoring box against **all** ground-truth instances of that prompted COCO category in the query image. It reports mean best IoU, localization recall at IoU 0.50 and 0.75, and presence recall at score 0.50. Negative episodes report mean max objectness and false-positive rate at score 0.50. Per-category results and macro positive IoU are stored in the metrics JSON.

The episodic metrics remain class-conditioned localization/presence diagnostics; they are not AP. Standard COCO AP/mAP is provided separately by `COCOeval`, over the complete per-category query-image set after support images are held out. Both metrics are useful: episodic IoU/presence is easy to inspect, while COCO AP measures ranked detections and false positives across images. A one-step smoke run only checks plumbing and is not a meaningful accuracy result.

## Inference with separate images

Repeat `--support-example` for each support box, using the same integer group for shots of one concept. Repeat `--query-image` for multiple query images; specify `--query-group` once per query when querying more than one concept. All query groups must have a corresponding support example group.

```bash
uv run python scripts/infer_promptable.py \
  --checkpoint logs/promptable_fewshot_1shot.best.pt \
  --support-example support.jpg 120 60 340 400 17 \
  --support-example support2.jpg 85 45 275 360 17 \
  --query-image query_a.jpg --query-group 17 \
  --query-image query_b.jpg --query-group 17 \
  --resolution 560 --num-queries 100 --device cuda \
  --output logs/support_query_predictions.json
```

Coordinates in support examples are pixel `xyxy` in the original support image. Predictions are pixel `xyxy` boxes in each query image.

## Compact end-to-end smoke

For fast code-path validation, use a temporary COCO subset and reduce `--steps`, `--num-queries`, and `--max-figures-per-class`. Verify that support/query image IDs differ, metrics contain both seen and held-out sections, and a `prediction_gt` figure is emitted. Do not use smoke metrics as experiment results.
